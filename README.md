# ClearPrint · 批量去水印

网页版批量去水印工具。**把整个文件夹拖进来，标一次水印位置，一键批量处理，打包下载 ZIP。**
所有计算都在你自己的浏览器里完成，**图片不会上传到任何服务器**。

> ### 在线用：<https://baiqz.github.io/clearprint/>
>
> 打开就能用。**半透明水印这条通路（最常见的那类）零下载、秒级出结果。**
>
> 在线版与本地版的唯一区别在「AI 生成式修复」：199MB 的模型放不进 GitHub 仓库
> （单文件上限 100MB），所以站点把模型**切成 3 块**（各 66MB）随页面一起发布，
> 要用的时候按序拉下来拼回原样 —— **同源加载，不依赖任何第三方**。
> **要最稳最快、且完全离线，仍然推荐本地跑 —— 见下面「怎么用」。**

## 怎么用（本地版，推荐）

```
python serve.py
```

然后浏览器打开 <http://127.0.0.1:8788>。

> ⚠️ 不能直接双击 `index.html`（`file://` 下 Worker 会被拒绝、模型也读不到）。
> 必须用 `serve.py` 起本地服务 —— 它会带上 COOP/COEP 跨源隔离头，
> 这是浏览器启用多线程 WASM 的前提。
> 真要是双击了，程序会在页面顶部把原因和正确做法直接写出来（见下文）。

### 本地版要先放模型

仓库里**不含** `models/lama_fp32.onnx`（199MB，超 GitHub 单文件上限）。
只做半透明水印的话不需要它；要用 AI 修复请从这里下载：

<https://github.com/baiqz/clearprint/releases>

下载后放到 `models/lama_fp32.onnx` 即可。**半透明水印通路不依赖模型。**

### 三步

1. **导入图片** —— 把整个文件夹拖进虚线框（或点「选择文件夹」）。支持 JPG / PNG / WebP，
   子目录会递归展开，非图片文件自动跳过。
2. **标出位置** —— 在图上涂抹水印所在区域。**只需涂一张**，勾上「把这张的涂抹套用到全部图片」
   即可批量复用（整批水印通常在同一位置）。也可以点「自动探测水印」让它先猜一个。

   - **画笔 / 橡皮**：默认是画笔，涂上红色标记；涂多了切「橡皮」擦掉（可反复修改）。
   - **笔刷大小**：拖动滑块调整，水印细就调小、大块就调大。
   - 涂的时候**比水印本身稍微大一圈**，把抗锯齿边缘也盖住，效果最好。
   - 图片两侧/上下的棋盘格区域**不是画布**，涂不上；图片有描边，一眼可辨。
3. **批量处理** —— 点「开始处理」，处理完点「打包下载 ZIP」。

## 两种处理通路（自动选路）

程序会先判断你的水印是哪一类，自动选最合适的方法：

| 水印类型 | 走哪条路 | 原理 | 速度 |
|---|---|---|---|
| **半透明水印**（常见的图库水印） | **半透明还原** | 逐通道 α 反解，代数还原被叠上去的像素 | 约 0.1 秒/张 |
| **实心水印**（不透明的字/logo） | **AI 生成式修复** | LaMa 神经网络把水印区域「画」回来（补纹理） | 约 20 秒/张 |

选路判据是「α 触顶率」：半透明水印反解出的 α 不会顶到上限（实测 0.0%），
实心水印会大面积顶满（实测 67.3%）。阈值 15%，两条路互不干扰。

也可以在「处理方式」里手动锁定某一条通路：
- **自动**（默认）：优先半透明还原，不合适再上 AI。
- **半透明水印还原**：快、细节完整，非透明水印效果差。
- **AI 生成式修复**：实心水印 / 压在复杂纹理上时用，慢但能补出纹理。

## 为什么半透明水印不能靠 AI 修

半透明水印下**原始像素其实还在**，只是被叠了一层。
AI 修复是「重新画一块」——糊在细密纹理（草地、织物）上会把纹理抹平。
α 反解是把叠加**算回去**，细节一根不丢。实测两者水印区误差都能降到 5 以内，
但纹理保真度差了整整一个量级（AI 32% vs 反解兜底约 0%——所以实心才交给 AI）。

## AI 模型没加载好会怎样（重要）

首次用 AI 修复要下约 198MB 模型。**模型没好，程序不会再「每张图各报一次错」**：

- 你要是**明确选了「AI 生成式修复」**：程序会先等模型就绪（最长 90 秒）再开工，
  并提示「AI 模型还在加载…」；等不到就整批不开工，只给一条原因。
- 你要是**用「自动」**：半透明水印照常秒出；只有真需要 AI 的图会等模型。
- 模型彻底不可用（404 / MIME 不对 / 被代理拦）时：**立即中止**，只标红已经开工的那 1~2 张，
  **其余保持「待处理」**，顶部给一条可读原因，并出现 **「重试失败项」** 按钮。
  修好原因（重开 `serve.py`、刷新页面）后点一下就能继续，不用重新导入。

> 所以状态栏出现「已中止 · … 剩余 N 张未处理」是**正常保护行为**，不是又崩了。

## 部署到 GitHub Pages（在线版是怎么跑起来的）

Pages 是个纯静态托管，有两条硬约束，都跟这个应用正面冲突：

| 约束 | 影响 | 解法 |
|---|---|---|
| **不能自定义响应头** | 拿不到 COOP/COEP → `crossOriginIsolated=false` → SharedArrayBuffer 不可用 → onnxruntime 多线程起不来 | `coi-serviceworker.js`：用 Service Worker 把这两个头**注入**给页面自己的响应。首次访问会多刷一次页面，之后就正常 |
| **单文件上限 100MB**（git 推送硬限） | 199MB 的 `lama_fp32.onnx` 推不上去 | 切成 3 块（各 66MB）随站点发布，加载时按序拉取拼接。**同源**才是关键，见下 |

模型源的顺序（`js/clear-worker.js` 里的 `modelSources()`）：

- **本地环境**（`127.0.0.1` / `localhost` / `file://`）→ 只认同源 `models/` 单文件。
  失败就立刻说清，**不去等一个注定超时的外部请求** —— 否则会把「快速中止」
  拖成慢动作，连带让批处理的保护行为来不及生效。
- **线上** → ① 站点分块 `models/lama_fp32.onnx.p1|p2|p3`（同源，主路径）
  → ② 同源单文件（自部署时把模型放进站点目录即生效）
  → ③ 在线镜像（最后兜底）。

> **踩过的两个坑，都是「看着能用、浏览器里不能用」**：
>
> 1. **GitHub Release 不能当模型源**：release 资产看着能公开直链，但实测它的响应
>    **不带 `Access-Control-Allow-Origin`**，跨源 fetch 必被拦。
> 2. **第三方镜像 hf-mirror 也不行**：curl 访问它 CORS 头齐全（302 与最终 200 都回显 Origin），
>    但真实浏览器里**连它首页都过不了**，报 `corsError: MissingAllowOriginHeader`。
>
> 共同教训：**curl 会给出错误结论**（跨主机 302 会让它丢掉 Origin），
> CORS 是浏览器行为，只能拿真实浏览器判。另外排查时别停在 `Failed to fetch` 上 ——
> 打开 CDP 的 `Network` 域把 `corsErrorStatus` 打出来，才看得见 `MissingAllowOriginHeader`
> 这种真正的判据（脚本见 `_scratch/wm-v2/probe_hf.py`）。

「细节补充」两层的由来见下节。

## 不能双击 index.html 打开（会看到「需用本地服务打开」）

直接双击 `index.html` 时，页面顶部会出现一条橙色横幅告诉你原因，并且**「开始处理」是被锁住的** ——
这样你不会白等一场必然的失败。

为什么必然失败：浏览器**不允许 `file://` 页面创建 Worker**（它的 origin 是 `null`），
也读不到 AI 模型；而且 `file://` 下拿不到站内路径，模型文件根本没法寻址。

> 早先的版本在这一点上做得不好：双击打开后会照常放行，点「开始处理」才报一串
> `Failed to construct 'Worker': Script at 'file:///...' cannot be accessed from origin 'null'`，
> 看着像是图片出了问题。现在改成**打开时就拦下来，并直接写清正确做法**。

正确做法只有一个：

```
python serve.py      # 在项目目录执行
```

然后浏览器打开 <http://127.0.0.1:8788>。

## 细节自动补充是怎么做的（重要）

**老问题**：AI 修复的输出是 512×512 上采回来的，天然偏软。而旧版回贴按
「掩码羽化后 > 0.004」判据融合 —— 羽化会把值铺满整个 ROI 方形，于是
**整个 ROI 方块都被换成这份软图**。实测（2048×1536 图、381×91 的中水印）：

| | 旧版 | 现在 |
|---|---|---|
| ROI 边长 | 977（占全图 30%） | **595（占 11%）** |
| AI 缩放比 | 0.52x | **0.86x** |
| 水印区纹理保真 | 39% | **55%** |
| 水印区残差 | 2.24 | **1.46** |
| 水印外围改动像素 | 约 95 万 | **2.4 万** |

**为了修 1% 的水印，赔上 30% 的画面** —— 这就是「细节没补回来」的真实来源。

**现在的三段式回贴**：

1. **核心区**（真正被水印盖住的范围）→ 交给 AI 重建，元素从这里长回来；
2. **融合带**（核心外扩一圈）→ **AI 的低频（色调/结构）+ 原图的高频（纹理细节）**
   按渐变权重合成，既接得上色、又保得住细节，且不会出现硬接缝；
3. **带外** → **一个像素都不动**，保持原图全部分辨率。

另外 ROI 外扩比例（`contextMargin`）有个反直觉的坑，已写成断言守住：
**外扩越大反而越糊** —— 因为输入恒为 512²，ROI 越大缩得越狠。
所以「细节补充」的 `强` 档是**收紧** ROI（0.15），把 512 的像素预算集中花在水印周围，
而不是放大参考范围（实测 ctx 0.45 → 缩放 0.69x → 锐度 1.945；
ctx 0.15 → 缩放 0.99x → 锐度 2.196）。

侧栏「细节补充」可选 **标准 / 强 / 关**，只影响 AI 生成式修复这条通路。

## 注意

- 首次加载要下载约 198MB 模型（**只在你要用 AI 修复时才下**；纯半透明水印不需要）。
  模型缓存在浏览器里，只有第一次慢。
- 处理结果默认导出 JPG（体积小）。需要无损可在「输出格式」里选 PNG。
- 水印要涂得比实际水印**稍微大一圈**，把抗锯齿边缘也盖住，效果最好。
